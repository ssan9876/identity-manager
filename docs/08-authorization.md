# 08 — Authorization model

Authorization has **three independent dimensions**. All of them apply to every guarded
route, and none subsumes another.

1. **Action** — does the actor hold this permission *anywhere*?
2. **Scope** — does their holding cover *this particular resource*?
3. **Rank** — for privilege writes, does the target *outrank* them?

## Identity resolution

An authenticated Keycloak principal becomes a local **Actor** by matching
`preferred_username` against `users.username`.

The resolution **fails closed**:

- No matching local user → denied.
- Local user whose `status` is not exactly `active` → denied. This is an **allow-list**
  (`=== 'active'`), not a deny-list of known-bad statuses, so a status added to the enum
  later is denied by default rather than granted by default.
- Resolved **fresh on every request**, never cached — a revoked or deactivated account
  is denied on the very next request, not after a cache expiry.

`GET /me` is the one deliberate exception: it is a pure echo of already-verified JWT
claims and does not resolve an actor at all. A client that needs "is this account still
active right now" must use `/self` or any permission-gated route, never `/me`.

## Actions

The complete catalog (`apps/api/src/authz/actions.ts`) holds **24 actions** — verify
with `f.actions.length` in `docs/.facts.json`, regenerated by
`node scripts/extract-doc-facts.mjs`:

| Action | Governs |
|---|---|
| `user:read` | Reading people; also gates the attribute-definition catalog |
| `user:create` | Creating people; also gates CSV import preview **and** commit |
| `user:update` | Editing a person |
| `user:activate` | Activating a person — `pending`/`suspended` → `active` |
| `user:deactivate` | Deactivating a person |
| `group:read` | Reading groups, members and effective members |
| `group:create` | Creating a group |
| `group:update` | Editing a group's name, description, attributes |
| `group:manage_members` | Adding/removing user members and nested child groups |
| `org_unit:read` | Reading the org tree |
| `org_unit:create` | Creating an org unit (always a **child** — see below) |
| `role:assign` | Reading, granting and revoking role assignments |
| `audit:read` | The audit log and outbox dead letters |
| `connector:read` | Connector target config and health |
| `connector:manage` | Editing target config, attribute mappings, running reconciles, and the HR-source admin surface (create/edit/preview) |
| `sso_app:read` | Reading registered SSO applications |
| `sso_app:manage` | Registering, editing, enabling/disabling, minting client secrets |
| `business_role:read` | Reading a business role, its formula, conflict rules/violations and mining recommendations |
| `business_role:manage` | Creating, editing, drafting, simulating, publishing and enabling/disabling a business role; conflict rules; access exceptions; mining drafts |
| `recert:read` | Reading recertification campaigns, their items and progress |
| `recert:manage` | Creating, opening and closing a recertification campaign — **not** deciding an item; see the reviewer note below |
| `organization:read` | Listing and reading tenant organizations |
| `organization:create` | Creating a tenant organization — and, as a side effect, its root org unit |
| `organization:update` | Suspending or reactivating a tenant organization |

Both `sso_app` actions are **global grant only** and held by `super_admin` alone.
Global-only because an application belongs to no org unit, so a scoped grant has
nothing to narrow to — the same rule that already governs the audit log, dead letters,
connector targets, attribute mappings, business roles, recertification campaigns and
organizations (all below). Deliberately not `user_admin`, which otherwise holds every
create/update action here: minting OAuth clients is realm-security work, not people
administration. Unlike `connector:read`, the `sso_app:read` reads are **not**
scoped-friendly either — `GET /sso-apps` and `GET /sso-apps/:id` both demand a global
`sso_app:read` grant (`SsoAppsController.requireGlobalGrant`).

`business_role:manage`, `recert:manage`, and all three `organization:*` actions are
likewise **global grant only** — none of their resources has a containing org unit.
`business_role:read` and `recert:read` are the exception among these: deliberately
scoped-friendly, like `connector:read`, because reading a formula or an attestation
record is ordinary visibility work, not the structural capability the `:manage` guard
exists for.

`organization:read` is additionally held by `super_admin` **alone** — the one `:read`
action deliberately absent from `READ_ONLY_ACTIONS`. Enumerating every tenant on the
deployment is platform-operator visibility, not directory work an `auditor`,
`user_admin` or `read_only` role needs to do theirs.

The recertification **reviewer** surface (`RecertReviewsController` —
`GET /recert/my-reviews`, `POST /recert/items/:id/decide`) is deliberately **not**
gated by any action at all: deciding an item is gated on identity (the item's own
resolved reviewer, or a holder of a *global* `recert:manage` grant), because reviewers
are ordinary managers who legitimately hold no role in this catalog. See "Guard
coverage is tested" below.

## Roles

| Role | Rank | Actions |
|---|---|---|
| `super_admin` | 40 | **everything** — all 24 actions |
| `user_admin` | 30 | all `user:*`, all `group:*`, `org_unit:read`, `business_role:read`, `recert:read` |
| `help_desk` | 20 | `user:read`, `user:update`, `group:read`, `org_unit:read` |
| `auditor` | 10 | `user:read`, `group:read`, `org_unit:read`, `audit:read`, `connector:read`, `business_role:read`, `recert:read` |
| `read_only` | 0 | `user:read`, `group:read`, `org_unit:read`, `business_role:read`, `recert:read` |

**The catalog is static code, not database rows.** A permission table is itself a
privilege-escalation surface; these grants should change only through code review. It is
built on `Object.create(null)`, so a lookup with a key like `constructor` or
`__proto__` resolves to `undefined` rather than an inherited, truthy value — `role_key`
is a Postgres enum, and `ALTER TYPE role_key ADD VALUE 'constructor'` is ordinary valid
SQL.

Notice what is **not** granted:

- `role:assign` — only `super_admin`. Getting role assignment wrong is privilege
  escalation, so nothing below the top of the catalog can touch it.
- `connector:manage` — only `super_admin`, deliberately mirroring `role:assign`. Editing
  target config or triggering a reconcile (**including a dry run**, which still makes a
  real outbound call) is a structural, directory-wide capability with outsized blast
  radius, not ordinary directory work.
- `auditor` gets `connector:read` but not `connector:manage` — per-target health and
  dead letters are the same category of operational visibility that role exists to see.
- `business_role:manage`, `recert:manage`, `sso_app:manage` and all three
  `organization:*` actions — only `super_admin`. Each is a global, directory- or
  tenant-wide capability with outsized blast radius, on the same footing as
  `role:assign` and `connector:manage`. `business_role:read` and `recert:read` are
  the exception: those two join `user_admin`, `auditor` and `read_only`, because
  reading a formula or an attestation record is ordinary "why does this person have
  this" visibility, not the structural capability `:manage` guards.

## Scope

A role assignment carries a **scope**: an org unit, or `NULL` for global.

Scope is evaluated over the org tree's `ltree` path, so it is **transitive** — an actor
scoped to `acme.sales` reaches `acme.sales.emea` and everything below it.

`PermissionEngine.scopePathsFor(actor, action)` returns:

| Return | Meaning |
|---|---|
| `null` | **Unrestricted** — every assignment granting this action is global |
| `[]` | **Entitled nowhere** — holds the action, but at no reachable scope |
| `['acme.sales', …]` | The paths the actor's grants cover |

`null` and `[]` are never collapsed. An empty array means "filter that matches nothing"
and produces an empty page — never, ever the unfiltered list.

### How scope is applied

- **List endpoints** filter both `items` **and** `total`. A scoped operator never sees a
  count implying records they cannot open.
- **Single-resource reads and writes** call `assertCanIn(actor, action, orgUnitId)`.
- **An out-of-scope resource that exists returns 403, not 404.** The directory's
  existence is not secret; its contents are.
- **A group with `orgUnitId = NULL` is global, but reads and writes are asymmetric.**
  Reading it follows the original rule — visible to any actor holding `group:read` at
  *any* scope. Writing to it does not: `GroupsController.requireGroup` demands a
  **global** grant of the write action itself (`group:update` or
  `group:manage_members`), not merely a grant of it somewhere. `SyncWorker.reconcileUser`
  pushes local group membership into real Keycloak groups — a downstream authorization
  primitive with cross-org reach — so "any scope, anywhere" would be too broad a grant
  for changing a group with no containing scope at all. See the global-grant table
  below.

### Where a global grant is required

Some resources have **no containing org unit**, so there is nothing to narrow a request
*to*. For these, holding the action somewhere is not enough — the grant itself must be
global (`scopePathsFor(...) === null`):

| Route | Why |
|---|---|
| `GET /audit` | `audit_log` has no org unit, and snapshots name principals from other org units. A scoped view would be silently partial. |
| `GET /outbox/dead-letters` | Events are keyed by `(aggregate, target)` with no org unit, and carry raw target error text. |
| `PATCH /connector-targets/:target` | Global infrastructure. A Sales-scoped admin could otherwise disable `keycloak` and stop credential sync organisation-wide. |
| `POST /connector-targets/:target/reconcile` | Walks the **whole** directory and pushes every principal. |
| `POST`/`PATCH`/`DELETE /attribute-target-mappings/*` | Decides what data leaves the system, for everyone. |
| `POST`/`PATCH /hr-sources/*`, `POST /hr-sources/:id/preview` | Same reasoning and the same helper shape as connector targets: an HR feed is organization-wide infrastructure, and a sync run writes people across the whole tenant. `GET /hr-sources/*` stays scoped-friendly, mirroring `connector:read`. |
| Every `/sso-apps` route, **including the reads** | An application belongs to no org unit. Unlike connectors, even `GET /sso-apps` and `GET /sso-apps/:id` demand a global grant — there is no scoped-friendly read here. |
| Every mutating `/business-roles` route (`business_role:manage`) | A role's formula spans the whole directory and its grants can place anyone into any group. Reads (`business_role:read` — list, get, conflicts, violations, mining recommendations) stay scoped-friendly. |
| `POST /recert-campaigns`, `POST /recert-campaigns/:id/open`, `POST /recert-campaigns/:id/close` | A campaign belongs to no org unit and its review set spans the whole directory. Reads (`recert:read`) stay scoped-friendly; deciding an item is a separate, identity-gated surface (see Actions above). |
| Every `/organizations` route, **including the read** | An organization is what org units hang *off* — nothing contains it. `organization:read` is additionally restricted to `super_admin` alone (see Actions above), the one read action never granted broadly. |
| `POST /groups` **with no org unit** | A global group's membership is pushed into real Keycloak groups. |
| `PATCH /groups/:id`, `POST`/`DELETE /groups/:id/members/*`, `POST`/`DELETE /groups/:id/child-groups/*` — **only when the target group itself has `orgUnitId = NULL`** | Same reasoning as creating one: `SyncWorker.reconcileUser` pushes membership into real Keycloak groups. A scoped write to an *org-unit-scoped* group still only needs `assertCanIn` as usual — this row applies only once the group being written to is itself global. |

Connector and HR-source **read** routes are deliberately left scoped-friendly: reading
non-secret config and a health status from a narrower scope is not the escalation;
mutating global infrastructure is. The same split applies to `business_role:read` and
`recert:read`.

**`POST /org-units` no longer has a global-only branch.** Every org unit this route
creates is a *child*, scoped by its parent — the request body's `parentId` is required
(Zod rejects a missing one before the handler runs), and the handler calls
`assertCanIn(actor, 'org_unit:create', parentId)`. The route used to accept an omitted
`parentId` and gate that case on a global `org_unit:create` grant, back when a root org
unit belonged to nothing; that branch is gone. A root org unit now belongs to an
**organization**, which owns exactly one, and the only thing that creates one is
creating the organization — itself gated on a global `organization:create` grant, in
the table above. `OrgUnitsRepository.createRoot` survives as the method organization
creation calls internally, but it is not reachable from HTTP.

## Rank — privilege guards

Two guards protect role assignment specifically.

### `assertCanAssignRole(actor, roleKey, scopeOrgUnitId)`

You may only grant a role **you hold yourself**, at a scope **your own holding covers**.

The critical case: **a scoped holding can never produce a global grant.** A
`super_admin` scoped to Sales cannot grant global `super_admin` — that is exactly the
path that turns a departmental account into a domain-wide one.

### `assertCanModifyPrincipal(actor, targetUserId)`

The target must not **outrank** the actor, by `ROLE_RANK`. This is independent of scope
entirely: a `help_desk` scoped to Sales must not be able to touch a global `super_admin`
who happens to sit in Sales.

Rank also guards ordinary user writes — `PATCH /users/:id`, `POST
/users/:id/deactivate`, and every import row — so a lower-ranked admin cannot edit or
deactivate a higher-ranked one.

### The four checks on a role write

Both `POST /users/:id/roles` and `DELETE /users/:id/roles/:assignmentId` run all four,
in this order:

1. `@RequirePermission('role:assign')` — do you hold it anywhere?
2. `assertCanIn(actor, 'role:assign', target.orgUnitId)` — can you reach this **person**?
3. `assertCanAssignRole(...)` — may you grant **this role** at **this scope**?
4. `assertCanModifyPrincipal(...)` — does the target **outrank** you?

Check 2 is ordered first among the three handler-level checks: there is no reason to
reveal "you may not grant this role at this scope" to an actor who cannot reach the
target user in the first place.

**Revoke evaluates all four against the grant being removed**, using the assignment
row's own `roleKey`, `scopeOrgUnitId` and `userId` — never re-trusting the URL. An actor
who could not have created a grant must not be able to destroy it, or revocation becomes
a side door around assignment's own narrowing.

`:assignmentId` must belong to `:id`: a real assignment id belonging to a different user
returns 404, exactly like a nonexistent one.

## Bootstrapping

Every grant path the API exposes requires the grantor to already hold `role:assign` —
which nobody does on an empty database. `pnpm bootstrap:admin` is the only way out, and
it **bypasses all four checks deliberately**.

It is a local operator script, not an HTTP route, and it is not wired into the Nest
application at all. Anyone able to run it already holds `RUNTIME_DATABASE_URL`, which is
already enough to read and write every row directly — so granting `super_admin` through
it adds no capability beyond what that access already implies. It just does it through
the application's own repositories instead of raw SQL.

## Debugging a 403

Work down this list:

1. **Is there a local user row?** The principal's `preferred_username` must match
   `users.username` exactly (case-insensitively). No row → 403 on everything. Run
   `bootstrap:admin`.
2. **Is that user `active`?** `pending`, `suspended` and `deactivated` are all denied.
3. **Do they hold the action at all?** `GET /self/permissions` returns their effective
   action list. An empty list is a valid state, not an error.
4. **Does their scope cover this resource?** Remember: an out-of-scope resource that
   exists is 403, not 404. If the message mentions scope narrowing, this is it.
5. **Does the route need a global grant?** See the table above. The error message says
   so explicitly and explains why.
6. **For a role write** — do they hold the role being granted, at a scope covering the
   grant, and does the target outrank them?

`GET /self/roles` returns the caller's own assignments, which is what the console's
scope picker uses.

## Guard coverage is tested

`guard-coverage.spec.ts` asserts that every controller carries `JwtGuard` and — unless
explicitly listed in its `AUTHENTICATION_ONLY` set — `PermissionGuard` with a
`@RequirePermission` on every route. That set holds four exemptions, each authenticated
but never permission-gated, resolving authorization from the caller's own identity
instead of a grant:

- `MeController` — `GET /me`, documented above.
- `SelfServiceController` — the `/self` routes, documented above.
- `AccessRequestsController` — the self-service access-request catalogue
  (`GET /access-requests/catalogue`, `mine`, `inbox`; `POST /access-requests`,
  `:id/cancel`, `:id/approve`, `:id/deny`). Every route serves the authenticated caller
  as themselves — browsing, requesting, cancelling, or deciding a request as the
  *resolved approver*, an ordinary manager holding no admin role and no permission
  grant at all.
- `RecertReviewsController` — `GET /recert/my-reviews`, `POST /recert/items/:id/decide`.
  A campaign's resolved reviewers are ordinary managers who legitimately hold no role
  in the static catalog; see the reviewer note under Actions above.

A new controller added without guards, or without being deliberately added to one of
`OPEN_BY_DESIGN` or `AUTHENTICATION_ONLY`, fails the suite.
